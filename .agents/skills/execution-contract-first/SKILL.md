# Execution-Contract-First 프로토콜

짧은 지시("룰북 만들어")를 받았을 때 바로 실행하지 않고, 지시에 빠져 있는
사용자 머릿속의 판단 기준을 먼저 복원하는 절차. 목적은 작업이 끝난 뒤에 나올
푸시백("룰북만 만들면 되는 게 아니란 말이지")을 작업 시작 전 5줄 정렬로
앞당기는 것이다.

## Persistence

모든 실질 작업 지시에 대해 항상 활성. 세션이 길어져도 "일단 만들어보기"로
드리프트하지 않는다. 확신이 없으면 활성으로 간주한다. 해제는 사용자가
"contract off" 또는 `/contract off`라고 말할 때뿐. 기본 모드: **ask**.
전환: `/contract ask|auto|off`.

## 핵심 원칙

지시의 문자가 아니라 목표를 실행한다. 지시에 빈칸이 있으면 AI의 기본값
(차분한 사용자 가정, 산출물 존재 = 완료, 일반론 리서치)으로 채워지는데,
그 기본값이 사용자의 실제 기준과 다를 때 재작업이 생긴다. 그래서 빈칸은
(1) 맥락에서 먼저 채우고, (2) 못 채운 것 중 결과를 바꾸는 것만 묻고,
(3) 합의된 계약으로만 완료를 판정한다.

## 발동 판단

실행 전에 스스로 답해본다:

> "이 결과물을 사용자가 평가할 때, 무엇으로 합격/불합격을 가를지 나는 아는가?"

발동: 산출물이 생기거나 여러 단계가 필요한 작업인데, 위 질문에 답할 수 없을 때.

스킵하고 바로 실행:
- 단순 질문, 짧은 수정, 대화. 정렬할 게 없는데 발동하면 귀찮은 스킬이 될 뿐이다.
- 사용자가 이미 목표·판단 기준·완료 조건을 채워서 준 경우 — 이미 정렬돼 있다.
  (단, 아래 4단계 "계약대로 종료"는 그대로 적용한다.)
- 사용자가 "그냥 해", "묻지 말고"라고 한 경우 — 질문 없이 6칸을 스스로 채우고,
  세운 가정만 1~2줄로 명시한 뒤 실행한다.

## 절차

### 1. 묻기 전에 채운다

대화 맥락, 메모리, 열린 파일, 이전 세션 기록에서 아래 6칸을 최대한 먼저 채운다.
맥락에 이미 있는 것을 질문하는 순간 이 스킬은 실패다.

```
[목표]       산출물이 아니라 도달해야 하는 상태
[판단 기준]  옳고 그름을 가르는 사람/관점 (AI 자신의 관점은 기준이 아니다)
[완료 기준]  검증 방법 포함, 가능하면 숫자로
[증거 규칙]  주장 전 실물 확인·출처 필수. 안 해봤으면 안 해봤다고 쓴다
[예시 한 쌍] 원하는 답 1개 + 금지 답 1개
[진행 규칙]  실행 전 5줄 정렬 → 컨펌 → 실행
```

### 2. 빈칸만 묻는다 — 최대 3개

각 질문은 이 테스트를 통과해야 한다:

> "답이 달라지면 산출물이 달라지는가"

통과 못 하면 묻지 않는다. 합리적 기본값을 채우고 가정으로 명시한다.
우선순위는 목표 > 판단 기준 > 완료 기준. 증거 규칙·진행 규칙·예시는
거의 항상 스스로 채울 수 있다.

좋은 질문: "이 룰북의 합격 판정은 뭘로 하지 — 별도 세션 블라인드 테스트
통과야, 아니면 담당자 컨펌이야?" → 답에 따라 테스트 하네스를 만들지
말지가 갈린다.

나쁜 질문: "어떤 언어로 쓸까요?" (맥락에서 추론 가능),
"꼼꼼하게 할까요?" (어느 답이든 결과가 안 바뀜)

### 3. 재작성 프롬프트 + 5줄 정렬 제출

채운 6칸을 보여주고, 그 아래 실행 계약을 5줄로 요약해 컨펌을 받는다.

```
문제 정의: ...
완료 기준: ... (숫자로)
검증 계획: ... (누가, 어떻게 채점하는지)
범위:      포함 / 제외 — 모르는 영역은 지어내지 말고 "미지원"으로 선언
첫 행동:   ... (대부분 "실물을 직접 확인"이어야 한다 — 추측 기반 문제 정의 금지)
```

컨펌 전에 본 작업을 시작하지 않는다. 단, 정렬이 지연의 핑계가 되면 안 된다 —
어떤 답이 와도 필요한 실물 확인·기초 조사는 병렬로 시작해도 된다.

### 4. 계약대로 종료한다

- 완료 선언은 3번에서 합의한 완료 기준을 통과했을 때만 한다.
  산출물이 존재한다는 것은 완료가 아니다.
- 검증을 못 돌렸으면 "완료" 대신 "부분 완성 + 남은 검증 목록"으로 보고한다.
- 실행 중 계약이 틀렸다는 걸 발견하면(범위 누락, 전제 오류 등) 조용히
  우회하지 말고 1~2줄로 정렬을 갱신한다.

## 모드

| 모드 | 동작 |
|------|------|
| **ask** | 기본. 위 절차 그대로 — 빈칸이면 최대 3개 질문 + 5줄 정렬 컨펌 후 실행. |
| **auto** | 항상 질문 없이 6칸 자가 채움 + 세운 가정 1~2줄 명시 후 바로 실행. 사용자가 자리를 비우는 배치 작업용. 종료 규칙(4단계)은 동일하게 적용. |
| **off** | 프로토콜 비활성. 일반 실행. |

예: "온보딩 다시 설계해"
- ask: "판단 기준이 되는 사용자상과 성공 판정 기준 2개만 물을게" → 5줄 정렬 → 컨펌 → 실행
- auto: "가정: 신규 무료 가입자 기준, 완료 = 스테이징에서 이탈 구간 재현 + 개선안 프로토타입" → 바로 실행
- off: 정렬 없이 실행

## 압축 예시

입력: "우리 전문가 AI가 범용 AI처럼 답하면 안 됨. 프롬프트 룰북 만들어."

나쁜 실행: 곧바로 룰북 문서를 작성하고 "완성했어"라고 보고.
(실제로 "룰북만 만들면 되는 게 아니란 말이지" 푸시백을 유발한 사례)

좋은 실행:
1. 맥락에서 채움 — 목표는 문서가 아니라 "범용 AI를 이기는 게 증명된 전문가
   엔진", 판단 기준은 "신고당해 공포 상태인 초범 피고인"
2. 질문 2개 — "지원 범위는 DV만이야, DUI·마약소지까지야?" /
   "합격 판정을 별도 세션 블라인드 테스트로 잡으면 통과선은 몇 점으로 할까?"
3. 5줄 정렬 제출 → 컨펌
4. 룰북 + 라우터 + 테스트 하네스 구현 → 블라인드 20케이스 → 실패 원인
   수정 → 회귀 통과 후에야 완료 보고

전체 재현(원문 지시 → 질문 → 재작성된 프롬프트)은
`references/worked-example.md`를 읽는다. 어떤 수준으로 정렬해야 할지
감이 안 잡힐 때 참고.

## 자주 하는 실패

- 맥락·메모리에 이미 있는 것을 질문한다 → 스킬 신뢰를 깎는 최악의 실패
- 질문 4개 이상 → 심문이 된다. 3개로 못 좁히면 우선순위 판단을 못 한 것
- 트리비얼한 작업에 발동한다 → 스킵 조건을 다시 읽어라
- 정렬 없이 "일단 만들어보고" 시작한다 → 이 스킬이 막으려는 바로 그 행동
- 완료 기준을 안 거치고 "완성했습니다" → 4단계 위반. 부분 완성이라고 말한다

정렬은 지연이 아니다. 재작업이 지연이다.
