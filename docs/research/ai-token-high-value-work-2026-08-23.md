# 대규모 AI 추론 예산의 고가치 사용법

- 문서 성격: 약 3시간의 한정된 실행 창에 재사용할 수 있는 일반 연구·실행 템플릿
- 시간 표기: `T0`는 실제 작업 시작 시각이고 `T+3h`는 그로부터 3시간 뒤다. 실행할 때는 공급자 화면의 실제 한도와 종료 시각을 먼저 확인하고 별도 작업 기록에 절대 시각을 남긴다.
- 조사 범위: 긴 컨텍스트, 에이전트형 코딩, 병렬 독립 리뷰, 테스트 생성, 보안·품질 감사, 문서화·지식 정리
- 출처 정책: 공식 제품 문서·공식 엔지니어링 보고서·정부/표준기관 지침·원 논문만 사용했다. 공급자 자체 실험 수치는 외부 독립 재현 결과로 간주하지 않는다.

## 결론

**토큰이 많을 때 무조건 좋아지는 단일 작업은 없다.** 추가 토큰의 가치가 가장 커지는 일반형은 다음과 같다.

> 가치가 큰 문제를 독립된 탐색 레인으로 나눈다 → 각 레인이 별도 컨텍스트에서 증거를 만든다 → 하나의 산출물로 합친다 → 작성자와 다른 컨텍스트가 반증을 시도한다 → 테스트·빌드·출처·재현 절차 같은 외부 판정기로 끝낸다.

이 결론은 단순한 “여러 에이전트가 좋다”는 주장이 아니다. Anthropic의 다중 에이전트 연구 시스템 내부 평가에서는 폭넓은 병렬 검색 문제에서 다중 에이전트가 단일 에이전트보다 90.2% 높은 성능을 보였고, BrowseComp 성능 변동의 80%를 토큰 사용량만으로 설명했다고 보고했다. 동시에 다중 에이전트는 일반 채팅의 약 15배 토큰을 썼으며, 모든 참여자가 같은 컨텍스트를 공유해야 하거나 의존성이 많은 문제에는 맞지 않는다고 명시한다. 특히 코딩은 연구보다 실제 병렬화 가능한 부분이 적다. 따라서 이 수치는 **독립적인 breadth-first 탐색에서 토큰 탄력성이 컸다는 공급자 내부 결과**이지, 임의의 작업에 토큰을 15배 쓰면 품질이 오른다는 보장이 아니다. ([Anthropic 다중 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system))

실행 창이 약 3시간뿐이면 가장 안전한 기본 추천은 **“근거 기반 현황 감사 + 우선순위 보고서 + 독립 검증”**이다. 이미 명세와 자동 검증이 준비된 저장소라면 그 다음 선택은 **독립된 테스트/수정 묶음 또는 반복 마이그레이션**이다. 반대로 요구가 모호한 새 기능 전체 구현, 배포, 대규모 리라이트는 토큰은 많이 쓰지만 실행 창이 끝난 뒤 남는 검증 가능한 가치가 낮을 가능성이 크다.

## 추가 토큰의 가치가 커지는 조건

아래 조건을 많이 만족할수록 큰 토큰 예산을 쓰기 좋다.

1. **독립적인 탐색 방향이 여러 개다.** 서로 다른 출처군, 서브시스템, 위협 유형, 파일 묶음처럼 결과를 합치기 전까지 병렬로 진행할 수 있어야 한다. Anthropic은 복잡한 연구에서 리드가 3–5개 서브에이전트를 동시에 시작하고 각 서브에이전트도 도구를 병렬 호출하는 방식으로 수행 시간을 최대 90% 줄였다고 보고한다. ([Anthropic 다중 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system))
2. **정답을 판정할 외부 기준이 있다.** 테스트, 빌드 종료 코드, 린터, 정답 fixture, 전후 스크린샷, 원 출처, 재현 가능한 PoC처럼 pass/fail 또는 근거 강도를 모델의 자기평가 밖에서 확인할 수 있어야 한다. 인용된 Anthropic 코딩 지침도 에이전트에게 실행 가능한 검증 수단을 주는 것이 지켜보는 세션과 자율 실행 가능한 세션의 차이라고 설명한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))
3. **결과가 재사용 가능한 산출물로 남는다.** 테스트, 패치, 위협 모델, 이슈 목록, ADR, 실행 매뉴얼, 인용된 연구 노트, 진행 기록은 실행 창이 끝난 뒤에도 가치가 남는다. OpenAI의 장기 작업 가이드는 중요한 결정과 열린 문제를 대화 이력에만 두지 말고 열고 편집하고 diff할 수 있는 기억/산출물로 기록하라고 권한다. ([OpenAI Codex 장기 작업 가이드](https://cdn.openai.com/pdf/8a9f00cf-d379-4e20-b06f-dd7ba5196a11/OAI_WhitePaper_Codex-maxxing26.pdf))
4. **검토 비용이 생성 비용보다 작다.** 에이전트가 수십 개의 저신뢰 제안을 쏟는 대신, 각 결과가 위치·근거·심각도·재현법·추천 수정·검증 상태를 갖춰 사용자가 빠르게 채택/기각할 수 있어야 한다. OpenAI Codex Security도 위협 모델로 범위를 정하고 가능하면 샌드박스에서 후보를 압력 테스트해 신호와 잡음을 구분하는 방식을 사용한다. ([OpenAI Codex Security](https://openai.com/index/codex-security-now-in-research-preview/))
5. **작업 권한과 폭발 반경을 제한할 수 있다.** 격리된 worktree/branch, 읽기 전용 조사, 제한된 도구, 네트워크 제한, 되돌릴 수 있는 체크포인트가 있어야 한다. OpenAI는 장기 에이전트의 지속성이 원치 않는 행동의 기회도 늘린다고 보고하며, 고정 평가만으로 충분하지 않아 감시·중단·롤백이 필요하다고 설명한다. ([OpenAI 장기 실행 모델 안전 보고서](https://openai.com/index/safety-alignment-long-horizon-models/), [OpenAI Codex 운영 경계](https://openai.com/index/running-codex-safely/))
6. **첫 사례나 작은 표본으로 작업 패턴을 검증할 수 있다.** 인용된 Claude Code 지침은 대량 파일 작업 전에 2–3개 파일에서 프롬프트를 시험하고 실패 패턴을 고친 뒤 전체 fan-out을 실행하라고 권한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))

반대로 모델 등급과 도구 품질도 중요하다. Anthropic의 내부 분석에서는 구형 모델의 토큰 예산을 두 배로 늘리는 것보다 최신 모델로 바꾸는 효과가 더 컸다. 따라서 “낮은 품질의 추론을 많이 생성”하는 것보다 **적절한 모델 + 검색/코드 실행/테스트 도구 + 충분한 예산**의 조합이 낫다. ([Anthropic 다중 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system))

## 작업별 추천 순위

아래 순위는 특정 제품의 성능 보장이 아니라, **약 3시간 안에 많은 토큰을 유용한 산출물로 바꿀 확률**에 대한 근거 기반 휴리스틱이다.

| 순위 | 작업 | 토큰이 많을수록 가치가 커지는 조건 | 반드시 남겨야 할 증거 | 부적합한 경우 |
| --- | --- | --- | --- | --- |
| 1 | 복합 주제의 근거 기반 조사 | 출처군·쟁점·대안을 독립적으로 나눌 수 있고 최신 원문 검색이 필요함 | URL이 붙은 주장, 상충 근거, 불확실성, 최종 의사결정 메모 | 답이 한 문서에 있거나 출처 확인이 불가능함 |
| 2 | 고가치 산출물의 독립·적대적 리뷰 | 작성자와 리뷰어 컨텍스트를 분리하고 요구사항·정확성·보안·범위를 각자 검토함 | 발견 위치, 영향, 재현법, 필수/선택 구분, 수정 후 재검증 | 같은 에이전트가 자기 설명만 반복하거나 판정 기준이 없음 |
| 3 | 테스트 생성과 회귀 사냥 | 기대 동작과 금지 동작이 명확하고 테스트를 실제로 실행할 수 있음 | 처음 실패한 테스트, 수정 뒤 통과 결과, 기존 테스트·커버리지 변화 | 문서화되지 않은 비즈니스 규칙을 AI가 추측해야 함 |
| 4 | 위협 모델 기반 보안·품질 감사 | 신뢰 경계, 데이터 흐름, 고위험 경로, 자동 스캐너/샌드박스가 있음 | 공격 경로, 구체적 코드 위치, PoC 또는 도구 결과, 오탐 판정 | “OWASP 전부 봐줘” 같은 체크리스트 나열만 요구함 |
| 5 | 검증된 패턴의 반복 코딩·마이그레이션 | 첫 2–3개 표본이 통과했고 파일/모듈 소유권과 worktree가 분리됨 | 대상 목록, 항목별 OK/FAIL, diff, 테스트, 미완료 목록 | 새 아키텍처 결정이 중간마다 필요하거나 여러 작업이 같은 핵심 파일을 건드림 |
| 6 | 문서화·지식 정리 | 흩어진 결정과 운영 지식을 이후 사람이 반복 사용할 예정임 | 출처·날짜·결정 이유·검토 시점 상태가 있는 ADR/런북/인덱스 | 단순히 긴 대화를 더 길게 요약하거나 기준 시점 없이 상태를 단정함 |

### 1. 긴 컨텍스트·복합 조사

긴 컨텍스트의 가치는 **전부 한 번에 밀어 넣는 것**이 아니라 많은 자료를 탐색한 뒤 필요한 근거만 남기는 데 있다. 원 논문 *Lost in the Middle*은 관련 정보가 입력 중간에 있을 때 성능이 떨어지는 U자형 패턴과, 문서를 더 많이 넣어도 성능 개선이 일찍 포화되는 현상을 보였다. 인용된 Anthropic의 컨텍스트 엔지니어링 지침도 토큰이 늘수록 회상 정확도가 저하되는 “context rot”과 한계효용 감소를 명시하며, 가장 작은 고신호 컨텍스트를 목표로 한다. ([Liu et al., *Lost in the Middle*](https://arxiv.org/abs/2307.03172), [Anthropic 컨텍스트 엔지니어링](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))

따라서 고가치 설계는 다음과 같다.

- 각 조사원이 별도 컨텍스트에서 한 쟁점과 원 출처군만 깊게 읽는다.
- 원문 링크, 날짜, 직접 뒷받침되는 주장, 반대 근거, 미해결 질문을 구조화해 반환한다.
- 리드 컨텍스트에는 원문 전체가 아니라 압축된 결과와 검증할 핵심 링크만 넣는다.
- 합성자는 서로 충돌하는 결과를 해결하고, 마지막 검증자는 인용이 실제 주장을 지지하는지 샘플링한다.

Anthropic은 이 형태에서 서브에이전트가 수만 토큰을 써도 리드에는 보통 1,000–2,000 토큰의 증류된 결과만 반환하는 패턴을 제시한다. 이는 대량 토큰을 **깨끗한 별도 컨텍스트의 탐색 용량**으로 쓰는 방식이다. ([Anthropic 컨텍스트 엔지니어링](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))

### 2. 에이전트형 코딩과 병렬 독립 리뷰

코딩에서는 “많은 에이전트”보다 **분리 가능한 작업과 충돌 없는 작업공간**이 먼저다. OpenAI Codex 앱은 에이전트별 thread와 worktree로 병렬 작업의 충돌을 격리한다. 인용된 Anthropic 지침도 별도 worktree에서 여러 세션을 실행하고, 작성자와 다른 새 컨텍스트가 diff를 검토하는 Writer/Reviewer 패턴을 권한다. ([OpenAI Codex 앱](https://openai.com/index/introducing-the-codex-app/), [Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))

독립 리뷰가 가치 있는 이유는 리뷰어가 구현 과정의 자기합리화와 실패한 시도를 보지 않고 요구사항과 결과만 보기 때문이다. 다만 리뷰어에게 무조건 문제를 찾으라고 하면 건전한 코드에도 문제를 만들어내고 과잉 설계로 이어질 수 있다. 공식 지침도 정확성 또는 명시된 요구에 영향을 주는 gap만 필수로 보고하고, 나머지는 선택으로 구분하라고 경고한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))

장기 구현은 큰 목표 한 줄로 한 번에 시키지 않는다. Anthropic의 장기 에이전트 실험에서는 높은 수준의 “앱 전체를 만들어라” 프롬프트가 컨텍스트 중간에 반쯤 구현된 기능과 문서화되지 않은 상태를 남겼다. 기능 목록, 진행 기록, 재현 가능한 시작 명령, 작은 단위의 완료, 세션 시작/종료 테스트가 여러 컨텍스트를 잇는 핵심이었다. ([Anthropic 장기 에이전트 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))

### 3. 테스트 생성

테스트 생성은 병렬화와 외부 판정이 모두 가능해 토큰 예산을 쓰기 좋은 편이지만, **요구사항과 독립된 테스트 작성**이 전제다. 가장 좋은 구조는 다음과 같다.

1. 한 컨텍스트가 명세와 실제 버그 사례에서 테스트를 작성한다.
2. 테스트가 기존 구현에서 예상대로 실패하는지 확인한다.
3. 다른 컨텍스트가 테스트를 수정하지 않고 구현을 고친다.
4. 세 번째 컨텍스트가 happy path 누락, 경계값, 상태 전이, 동시성, 오류 복구를 검토한다.
5. 전체 관련 테스트·빌드·정적 분석을 실행하고 결과를 보존한다.

Anthropic 공식 지침은 실행 가능한 검증과 작성자와 다른 verification subagent를 권하고, 인용된 GitHub 지침은 AI 생성 테스트를 그대로 수용하지 말 것, happy path만 검사하지 말 것, 문서화되지 않은 비즈니스 규칙을 AI가 추측하게 하지 말 것을 명시한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices), [GitHub 테스트 커버리지 지침](https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/drive-downstream-impact/increase-test-coverage))

### 4. 보안·품질 감사

보안 감사는 토큰을 많이 쓸 만한 고가치 작업이지만, 자유로운 “취약점 찾아줘”는 오탐 보고서를 만들기 쉽다. 권장 레인은 다음처럼 서로 다른 질문을 맡는다.

- 자산·신뢰 경계·공격자 능력을 정의하는 위협 모델
- 인증/인가와 상태 전이
- 외부 입력에서 위험 sink까지의 데이터 흐름
- 파일·명령·네트워크·IPC 같은 권한 경계
- 의존성·비밀·구성·공급망
- 기존 테스트, 정적 분석, 동적 재현과 오탐 판정

OpenAI Codex Security의 공식 설명도 먼저 편집 가능한 프로젝트별 위협 모델을 만들고, 후보를 실제 시스템 맥락과 가능하면 샌드박스 PoC로 검증한 뒤 수정안을 제시한다. OWASP는 수동 리뷰가 SAST/DAST를 대체하는 것이 아니라 비즈니스 로직·복잡한 보안 구현·맥락 의존 취약점을 보완한다고 설명한다. NIST SSDF는 설계자와 독립된 자격 있는 사람 또는 자동 프로세스가 보안 요구와 위험 모델을 검토하고 결과를 산출물로 남기는 방식을 제시한다. ([OpenAI Codex Security](https://openai.com/index/codex-security-now-in-research-preview/), [OWASP Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html), [NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final))

AI 감사 결과만으로 안전 판정을 내리거나 즉시 배포해서는 안 된다. GitHub의 AI 생성 코드 검토 지침은 먼저 테스트와 정적 분석을 실행하고, 요구·아키텍처 적합성과 의존성·라이선스·환각 API·삭제되거나 건너뛴 테스트를 별도로 확인하며, 사람의 판단을 유지하라고 한다. ([GitHub AI 생성 코드 검토](https://docs.github.com/en/enterprise-cloud%40latest/copilot/tutorials/review-ai-generated-code))

### 5. 문서화·지식 정리

문서화는 토큰 소비량보다 **향후 반복 비용을 얼마나 없애는가**로 평가한다. 좋은 대상은 다음과 같다.

- 변경에서 확정된 설계 결정과 이유를 ADR로 정리
- 실제 명령으로 검증한 개발·테스트·복구 runbook
- 공개 API/IPC/데이터 흐름과 소유권 지도
- 중복·충돌·기한 경과 문서를 찾아 검토 기준일과 상태 표시
- 다음 에이전트가 읽을 짧은 규칙과 상세 문서 링크를 분리

긴 설명을 공통 컨텍스트 파일에 모두 넣는 것은 역효과다. 인용된 Anthropic 지침은 항상 로드되는 프로젝트 지침을 짧게 유지하고, 모델이 코드에서 알아낼 수 있는 내용과 상세 API 문서는 제외하며, 긴 규칙 때문에 실제 지시가 묻힐 수 있다고 경고한다. OpenAI 가이드도 영속 컨텍스트에는 코드에서 추론하기 어려운 명명 규칙, 비즈니스 로직, 알려진 특이점, 테스트·리뷰 관례를 넣는 방향을 제시한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices), [OpenAI가 Codex를 사용하는 방식](https://cdn.openai.com/pdf/6a2631dc-783e-479b-b1a4-af0cfbd38630/how-openai-uses-codex.pdf))

## 토큰 낭비가 되는 패턴

### 1. 저장소나 자료 전체를 한 컨텍스트에 밀어 넣기

긴 컨텍스트 창은 저장 용량이지 모든 토큰을 동일하게 잘 사용하는 보장이 아니다. 중간 정보 성능 저하와 context rot 때문에, 경로·인덱스·검색 도구를 주고 필요한 자료를 적시에 불러오게 하는 편이 낫다. 관련 없는 작업 사이에는 새 컨텍스트를 쓰고, 장기 작업의 결정·미해결 문제·변경 파일은 구조화된 메모로 넘긴다. ([Liu et al., *Lost in the Middle*](https://arxiv.org/abs/2307.03172), [Anthropic 컨텍스트 엔지니어링](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))

### 2. 여러 에이전트가 같은 의존적 문제를 동시에 풀기

공유 핵심 파일, 순차 의존성, 하나의 재현된 오류만 있는 작업에 에이전트를 복제하면 같은 조사와 충돌을 반복한다. Anthropic의 C 컴파일러 실험에서도 16개 에이전트가 모두 같은 실패에 막혔고, 독립적인 테스트 단위와 정답 oracle을 만들어서야 병렬성이 생겼다. 이 사례는 대량 토큰의 가능성을 보여 주지만 동시에 약 2,000세션, 21억 개가 넘는 입출력 토큰, 약 2만 달러가 든 극단적 실험이므로 일반 3시간 작업의 직접 기준으로 쓰면 안 된다. ([Anthropic 병렬 C 컴파일러 실험](https://www.anthropic.com/engineering/building-c-compiler))

### 3. “전부 개선해”, “완벽하게 만들어” 같은 무경계 목표

큰 목표만 주면 에이전트가 너무 많은 것을 한 번에 시도하고 조기 완료를 선언하거나 컨텍스트가 끝날 때 불완전한 상태를 남기기 쉽다. 요구사항, 범위 밖 항목, 완료 판정, 결과 위치, 실패 시 남길 정보가 있어야 한다. ([Anthropic 장기 에이전트 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [OpenAI Codex 장기 작업 가이드](https://cdn.openai.com/pdf/8a9f00cf-d379-4e20-b06f-dd7ba5196a11/OAI_WhitePaper_Codex-maxxing26.pdf))

### 4. 같은 에이전트의 자기검토만 반복하기

작성 맥락을 공유한 자기검토는 같은 가정과 맹점을 반복할 수 있다. 새 컨텍스트가 diff와 요구사항만 보고 반증하게 하되, 사소한 취향을 필수 결함으로 세지 않도록 중요도 기준을 준다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))

### 5. 실행하지 않는 테스트와 재현 없는 보안 보고서

코드처럼 보이는 테스트 수, 추정 취약점 수, 긴 설명은 검증이 아니다. 테스트의 최초 실패와 수정 후 성공, 스캐너 출력, 샌드박스 PoC, 코드 위치, 영향 경로가 없으면 토큰이 검토 부채로 바뀐다. ([GitHub AI 생성 코드 검토](https://docs.github.com/en/enterprise-cloud%40latest/copilot/tutorials/review-ai-generated-code), [OpenAI Codex Security](https://openai.com/index/codex-security-now-in-research-preview/))

### 6. 실행 창 종료 직전의 배포·병합·삭제·대외 전송

시간 압박은 권한 범위를 넓힐 근거가 아니다. 장기 실행일수록 원치 않는 행동 기회가 늘어나므로, 3시간 작업은 읽기 전용 보고서, 격리된 branch/worktree, 로컬 테스트, 초안에 머무르게 하고 외부 전송·배포·병합·삭제는 이후 사람 검토로 넘긴다. ([OpenAI 장기 실행 모델 안전 보고서](https://openai.com/index/safety-alignment-long-horizon-models/), [OpenAI Codex 운영 경계](https://openai.com/index/running-codex-safely/))

### 7. 토큰 소진 자체를 성공 지표로 삼기

Anthropic의 같은 연구에서도 최신 모델 선택이 구형 모델의 토큰 예산을 두 배로 늘리는 것보다 효과가 컸다. 성공 지표는 사용 토큰이 아니라 확인된 결함, 통과한 검증, 채택 가능한 결정, 절약된 사람 검토 시간, 남은 불확실성이다. ([Anthropic 다중 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system))

## T0–T+3h 상대 실행 설계

아래 시간표는 위 출처를 종합한 **재사용 가능한 실행 제안**이며 공급자 공식 처방이 아니다. `T0`를 실제 작업 시작으로 잡고 `T+3h`까지 실행한다. 실제 가용 시간이 더 짧으면 각 구간을 비례해 줄이되 마지막 10분 인계 버퍼는 유지한다.

| 상대 시간 | 단계 | 해야 할 일 | 종료 산출물 |
| --- | --- | --- | --- |
| T0–T+15m | 계약 고정 | 목표 하나, 범위 밖, 입력, 산출물 경로, 완료 기준, 허용 도구, 금지 행동을 1쪽 이하로 작성 | 작업 계약과 공통 판정표 |
| T+15m–T+80m | 3–5개 독립 레인 병렬 실행 | 연구라면 출처군/쟁점, 코드라면 모듈/테스트/위협, 감사라면 공격면을 겹치지 않게 배정 | 레인별 근거·패치·테스트·미해결 목록 |
| T+80m–T+125m | 합성·구현 | 중복 제거, 충돌 해결, 우선순위 부여, 한 산출물 또는 격리된 작은 변경으로 통합 | 검토 가능한 초안/diff |
| T+125m–T+155m | 독립 검증 | 새 컨텍스트가 요구사항 누락·반례·보안·범위 이탈을 검사하고 테스트/빌드/링크를 재확인 | 필수 결함 목록과 검증 로그 |
| T+155m–T+170m | 필수 수정 | 정확성·요구사항에 영향 주는 것만 수정하고 결정적 검사를 다시 실행 | 최종 산출물과 known limitations |
| T+170m–T+180m | 인계 버퍼 | 파일 저장, 변경·검증·실패·미완료 요약. 새 작업 시작 금지 | 실행 창이 끝난 뒤에도 읽을 수 있는 인계문 |

### 레인 선택 예시

복합 연구라면 다음 5개가 가장 자연스럽다.

1. 공식 문서와 사양
2. 원 논문과 공식 평가 저장소
3. 상충 근거·실패 사례·한계
4. 적용 대안과 비용/위험 비교
5. 출처 검증과 날짜·주장 대응 감사

코드 저장소라면 무관한 기능 5개를 동시에 고치기보다 다음처럼 한 목표를 다른 관점으로 덮는 편이 안전하다.

1. 대상 구조·요구사항 조사(읽기 전용)
2. 명세 기반 실패 테스트 작성
3. 구현 또는 작은 수정
4. 위협 모델·권한 경계 감사(읽기 전용)
5. 새 컨텍스트의 diff/요구사항 적대적 리뷰

테스트 작성과 구현이 서로 의존한다면, 테스트 작성자는 명세만 보고 먼저 작업하고 구현자는 확정된 테스트를 수정하지 않는 순서를 사용한다. 같은 파일에 쓰는 두 구현자는 병렬로 두지 않는다. 반복 마이그레이션은 먼저 2–3개 표본을 검증한 후에만 파일 묶음별 worktree로 확장한다. ([Claude Code 공식 best practices](https://code.claude.com/docs/en/best-practices))

## 바로 사용할 작업 지시문 골격

```text
실제 시작 시각: [T0의 절대 날짜·시각·시간대]
실제 종료 시각: [T+3h의 절대 날짜·시각·시간대]

목표:
- [실행 창이 끝난 뒤에도 가치가 남는 단일 결과]

완료 기준:
- [테스트/빌드/원 출처/재현 절차/전후 비교]
- 결과는 [한 문서 또는 격리된 diff]로 남긴다.
- 성공을 말로 주장하지 말고 실행 결과와 근거를 남긴다.

범위 밖:
- 배포, push, merge, 삭제, 외부 전송, 자격 증명 접근
- 명시되지 않은 리라이트와 새 의존성

병렬 레인:
1. [독립 질문/모듈/출처군]
2. [독립 질문/모듈/출처군]
3. [테스트 또는 검증]
4. [보안/품질 반증]

조정 규칙:
- 각 레인은 별도 컨텍스트와 격리된 소유 범위를 사용한다.
- 원문 전체 대신 주장-근거-URL/위치-불확실성만 합성자에게 보낸다.
- 같은 핵심 파일을 두 레인이 동시에 수정하지 않는다.
- T+125m부터 새 탐색을 중단하고 검증으로 전환한다.
- T+170m부터 새 작업을 시작하지 않고 인계만 작성한다.

최종 인계:
- 만든 것
- 검증한 것과 정확한 결과
- 실패하거나 미완료인 것
- 사람이 결정해야 할 것
- 다음 한 단계
```

## 선택 기준 한 줄 요약

대량 토큰을 쓸 작업은 다음 질문으로 고른다.

> **독립 탐색 수 × 외부 검증 가능성 × 산출물 재사용성 × 절약되는 사람 시간**이 **조정 비용 × 검토 부채 × 실패 폭발 반경**보다 큰가?

“예”라면 병렬 연구·테스트·감사·검증에 토큰을 쓴다. “아니오”라면 토큰이 남더라도 짧은 단일 작업으로 끝내는 편이 낫다. 사용량 소진보다 검증 가능한 가치 보존이 목표다.

## 근거의 한계

- Anthropic의 90.2%, 80%, 15배, 최대 90% 수치는 자사 연구 시스템과 내부 평가에서 나온 값이다. 다른 모델, 코딩 저장소, 개인 구독의 토큰 회계에 그대로 대입할 수 없다. ([Anthropic 다중 에이전트 연구 시스템](https://www.anthropic.com/engineering/multi-agent-research-system))
- OpenAI Codex Security의 오탐 감소와 발견 사례는 연구 프리뷰 공급자의 자체 보고다. 구조적 패턴(위협 모델 → 탐색 → 검증 → 패치)의 근거로만 사용하고 일반 정확도 보장으로 해석하지 않는다. ([OpenAI Codex Security](https://openai.com/index/codex-security-now-in-research-preview/))
- *Lost in the Middle*의 수치 실험은 2023년 당시 모델을 다룬다. 후속 모델의 정확한 저하량을 말하는 근거로 쓰지 않고, 인용된 공급자 문서가 경고하는 긴 컨텍스트의 위치·관련성 위험을 설명하는 원 논문으로 사용했다. ([Liu et al., *Lost in the Middle*](https://arxiv.org/abs/2307.03172), [Anthropic 컨텍스트 엔지니어링](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))
- NIST와 OWASP는 보안 개발·검토 절차의 근거이지, AI가 사람 보안 전문가를 대체한다는 증거가 아니다. ([NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final), [OWASP Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html))
