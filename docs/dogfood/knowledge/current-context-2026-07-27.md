## What the product is now

God of Sessions is a local decision and authority layer above provider-native
agent runtimes. Its job is not to replace their agent loops or reproduce their
session dashboards. Its bedtime promise is:

> Given the user's current goals, explicit project importance, installed route
> capabilities, fresh and source-specific capacity, workspace conflicts, risk,
> and wake time, choose what should run where, freeze the exact proposal for
> one approval, and verify the real outcome by morning.

The shortest public framing remains:

> Stop being the queue.

Supporting line:

> Every session. One clear next move.

Bedtime outcome:

> One bedtime approval. Verified work by morning.

## Revised product wedge

God of Sessions must own the portfolio decision **before** delegation:

> Read the user's actual fragmented histories and explicit priorities, decide
> which project deserves scarce unattended time, map it to a currently safe
> route with fresh capacity, explain every elimination, preserve “run nothing,”
> freeze one exact authority, and prove the outcome by morning.

The lower execution plane may eventually be provider-native, MCP Tasks,
Claudexor, or another compatible runtime. Rebuilding a mature multi-harness
control plane is not itself the product thesis. Morrow's defensible layer is
user-specific judgment and attention relief above those runtimes.

## Cycle 05 capacity correction

A second active synchronization window ran from **20:27:09 to 20:37:09 PDT**.
It narrowed the product trial to one vertical slice: recommend one or more
projects for tonight using the user's real remaining subscription capacity and
the commercial size of each plan.

Raw remaining percentages are not comparable across plan tiers. Claude Max 5x
and Max 20x provide five and twenty times Claude Pro capacity per session;
OpenAI's individual Pro tiers provide five and twenty times Plus capacity.
Accordingly, 5% remaining in a Claude Max 20x five-hour session is
approximately one complete Claude Pro session allowance, while 30% remaining
on a base plan is 0.3 base-plan allowances.

This conversion has limits:

- Anthropic's public 5x/20x guarantee is explicitly per session. Weekly and
  model-specific windows remain independent constraints and their exact tier
  denominators are not publicly guaranteed.
- Codex tasks consume a shared agentic pool at variable rates based on model,
  tokens, cache, complexity, and execution surface. A normalized allowance is
  a routing signal, not a promised task count.
- Current local Claude authentication exposes only generic `Max`; OpenClaw
  supplies live windows but no exact tier. Current Codex app-server supplies a
  plan type, but the commercial multiplier mapping needs an explicit source or
  user confirmation.

The product contract is now: preserve provider-native percentages and resets,
add a sourced base-plan-equivalent estimate for cross-plan comparison, and
show unknown or ambiguous tiers as a recovery action. The same evidence must
reach the advisor model and the human review. Missing tier evidence must never
default silently to 1x, 5x, or 20x.

Munin and VibeFocus invalidate two broader versions of this claim. Munin
already turns local Codex and Claude Code histories into checked proactive
next-step suggestions. VibeFocus already offers a code-aware AI portfolio
advisor across projects. The remaining hypothesis is therefore the complete
decision contract, not “AI recommends a project” by itself:

> recover candidates from fragmented real histories → let the user's chosen
> advisor model judge value and priority → deterministically enforce current
> capacity, workspace safety, route feasibility, and no-run → explain every
> elimination → freeze one exact authority → verify the morning outcome

The model owns semantic judgment. Code owns the candidate envelope and
authority boundary. The model cannot invent work, revive a blocked route, or
expand an approval.

The primary visual should be a decision graph:

`fragmented evidence → ranked candidates → constraints/eliminations → selected or no-run → exact authority → morning proof`

## Capacity is a typed, time-sensitive input

Do not hard-code “5-hour plus weekly” as the universal capacity model.

- Codex app-server currently exposes primary and secondary windows, reset
  timestamps, optional monthly limits, spend-control state, earned reset
  credits, and sparse live updates. Reset credits are separate, idempotent
  resources and require a fresh snapshot after use.
- Claude exposes rolling session and weekly limits, model-specific limits,
  optional extra usage, and `/usage` as the user-facing current source.
- Grok paid surfaces now draw from one shared weekly pool across Chat, Build,
  Imagine, Voice, and other products, with different compute costs and optional
  extra credits.

The planner should eventually consume typed `CapacityPool` observations:
provider/account identity, pool kind, used or remaining value, observation
time, reset time, freshness, shared-product scope, credits, and source. Missing
or stale data must lower confidence rather than silently become zero or
unlimited capacity.

## Provider integration boundary

- Codex app-server is an appropriate rich-client protocol. It supports managed
  ChatGPT login, persisted threads, streamed lifecycle events, approvals scoped
  by thread/turn/item, rate-limit reads, usage reads, and typed completion.
- Anthropic explicitly says third-party products may not offer Claude.ai login
  or route Free, Pro, or Max credentials on users' behalf. Productized Claude
  access should use an API key or supported cloud provider. Native Claude Code
  dispatch can still be treated as an installed local harness under its own
  supported authentication; do not copy consumer OAuth into God of Sessions.
- Hermes is useful implementation prior art, but its Anthropic OAuth notes do
  not override Anthropic's current developer terms.
- Six discovered session sources do not imply six executable routes. Route
  capability must come from a current preflight and installed-version contract,
  never from transcript search or upstream marketing.

## Exact authority is the current load-bearing contract

Current primary-source patterns converge:

- OpenClaw prepares one canonical `systemRunPlan`, stores it with the approval,
  reuses that exact plan for execution, and rejects changed command, working
  directory, agent, or session metadata as an approval mismatch.
- Codex scopes approval requests to thread, turn, item, and request identity;
  terminal `item/completed` state is authoritative.
- Grok keeps plan review independent from auto/always-approve and applies deny
  rules even under permissive modes.
- MCP requires correlation identifiers and tells clients to ignore unknown or
  already-completed elicitation IDs.

For God of Sessions this means:

1. The chat handoff must carry one frozen plan, not instructions to rebuild it.
2. Approval must be bound to a deterministic fingerprint of drafts,
   preflights, schedule, and requested duration.
3. A newer plan, changed duration, explicit invalidation, or expiry must make
   every older approval fail closed.
4. Reopening a persisted plan may restore review context but must not extend its
   authority window.
5. Stored plans must be revalidated before being registered for approval.

## Completion is not success

Claude Routines explicitly warns that a green run means the infrastructure
started and exited without an infrastructure error, not that the prompt's task
succeeded. MCP Tasks likewise distinguish durable execution state from the
result retrieved later.

Morning review is therefore a core product surface, not a polish feature. A
successful overnight item needs:

- the provider's durable run or task identifier;
- the exact frozen goal and route used;
- workspace start and end evidence;
- relevant tests or artifact checks with actual exit/result state;
- an independent outcome judgment;
- honest `blocked`, `failed`, `partial`, or `needs input` states.

MCP Tasks reinforces the runtime contract: create and persist a durable task
handle before responding, model `working` and `input_required` separately from
terminal states, never mutate a terminal state, and treat cancellation as
cooperative rather than assumed. Those are execution primitives, not proof
that the selected work was valuable.

## What current evidence says about human judgment

- OpenAI reports that context switching becomes painful around three to five
  concurrent Codex sessions and argues that work should be organized around
  deliverables rather than sessions.
- Anthropic's privacy-preserving analysis of roughly 400,000 Claude Code
  sessions finds that people still make most planning decisions while Claude
  makes most execution decisions. Task-specific domain expertise increases
  verified success and recovery from errors.
- Anthropic's long-running-agent work requires incremental scope, recoverable
  progress, and end-to-end tests rather than a long prompt and elapsed time.
- π-Bench distinguishes proactivity from task completion and finds that hidden
  intent and cross-session continuity remain difficult for frontier systems.

These findings support evaluating “choose the right work” separately from
“execute assigned work well.” They do not establish that Morrow currently
passes that evaluation.
